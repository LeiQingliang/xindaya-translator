# 输出模式与交付契约

用户格式要求优先于模式默认；目标语言使用已确认的任务设置。模式描述呈现方式，不授权删减、增添事实或执行额外外部操作。

## 呈现模式

| 模式 | 交付 |
| --- | --- |
| `clean`（默认） | 仅完整译文；保留标题、段落等结构，不加序言、自评或结语。 |
| `bilingual` | 按段落或句子逐一配对原文与译文；长文避免极宽的双列表格。 |
| `annotated` | 先译文，再给真正影响理解的术语、文化表达或歧义说明，和原文内容明确分开。 |
| `review` | 按用户要求提供可定位的错误、理由和修订稿；无实质错误时不要为了表现审校而强行改写。 |
| `literary` | 尊重作者声音、意象、节奏、反复与修辞功能，不擅自增加意象；创译仍需用户明确要求。 |

审校时先确认材料：有原文和译文才能判断忠实度；只有译文时只评价中文质量与内部一致性，并说明限制。只有原文且用户要求“翻译并审校”时，可译后复核，但不能声称存在独立人工验证。

## `structured` 是独立的格式约束

Markdown、JSON、HTML、字幕和配置等依据 [结构化内容指南](structured-content.md) 处理。它可以与呈现模式组合，但不能破坏既定格式：

- “只返回有效 JSON”：输出原始 JSON，不用 Markdown 围栏，不增添解释字段。
- “逐段对照，并保留原始 JSON 文件”：原始文件与对照文档分别交付；不要把原有字符串改成双语对象。
- “翻译 SRT”：保持 cue 和时间码，只翻译指定文本；注释不得变成额外字幕。
- 需要说明重大疑义时，放在允许的伴随消息/文件中；用户禁止任何附言且疑义无法保守解决时，先提出必要澄清，不把说明塞进交付物。
- 当用户要求彼此冲突、且没有自然兼容方案时，询问优先事项。不要悄悄牺牲严格格式或完整性。

## 示例请求

- “信达雅翻译成简体中文” → `clean`。
- “逐段中英对照，不要漏段” → `bilingual`。
- “翻译并解释专业术语” → `annotated`。
- “对照原文审校，列出影响含义的问题” → `review`。
- “翻译 README，保留 Markdown 和可执行代码” → `clean` + `structured`。
- “将这首诗译成中文，保留重复与节奏” → `literary`，并非自动创译。
